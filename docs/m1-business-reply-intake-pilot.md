# Business attendance reply intake pilot

This is an opt-in, read-only inbox pilot for Stu at Revolution and Trey at Richmond. It does not apply attendance corrections, send clarification emails, or release payroll. It does not read personal Gmail. All flags are absent/off in the prepared code. No production routing, OAuth grant, trigger, or external test email is performed by preparing this release.

## Operational route

The existing production Apps Script projects run one `pollBusinessAttendanceReplies` time trigger each, hourly, as **revbjjops@gmail.com**. Gmail is accessed only through API GET calls with `https://www.googleapis.com/auth/gmail.readonly`. The token is sent only to Google's fixed API host and is never retained or passed to Netlify. No new credential or service is needed for the proposed route.

Each project searches new attendance-marked replies from its own exact manager address: `info@revolutionbjj.com` or `info@richmondbjj.com`. These are the existing configured recipient identities, **not proof of the managers' actual reply From addresses**. Verify the actual From in the live acceptance test. An alias needs explicit canonical configuration; do not guess from a display name.

The existing authenticated digest supplies an immutable event ID, dated attendance questions, exact class labels, original row IDs/fingerprints, day attendance hash, canonical full instructor names already present in attendance, and the established payroll period. A small subject marker connects the future email to that event. The sender only changes Reply-To after explicit route-verification and routing flags. Existing To/BCC copies and permanent gym/day send claims remain intact. Legacy/unmarked messages and failed digest fallbacks keep the old route.

The poller posts minimized records using the existing per-gym HMAC secret to `/api/m1-reply-intake`. Records are confined to `reply-intake/v1/` inside:

- `gib-m1-digest-production-rev-delivery-v1`
- `gib-m1-digest-production-richmond-delivery-v1`

No existing outgoing key is updated or deleted. Strong reads and immutable create-only writes verify retained data. Mail is not marked read, labeled, moved, deleted, or sent. Attachments are not downloaded. Only new plain text is retained, at most 12,000 characters; quoted history is removed. Missing/HTML-only/truncated content stays unresolved. Wrong sender/recipient and missing-event records retain metadata only, without the body or an agent wake hint.

For an exact thread match, the reply must belong to the Gmail thread containing the uniquely matched SENT parent, reference its RFC Message-ID, and match its event-marked subject, recipient and business Reply-To. DMARC and actual parsed sender must match. MailApp's return value is **not** a provider message ID. Whether the existing MailApp projects leave a usable SENT parent has not been proven by local tests; live acceptance must establish it. Missing parent evidence is retained as review-needed, never guessed.

## Private review and state boundaries

The endpoint offers authenticated Admin `action: "read"` POST and GET with the existing same-origin/session checks, plus a signed own-gym `action: "read"` POST. Browser readers use POST because same-origin GET may omit `Origin`. `readBusinessAttendanceReplyQueue` provides the signed path from the already trusted production project without copying its credential. No public queue page is published. The real goati/operator access path still needs to be exercised on the deployed receiver before activation; a local authentication test is not a live access test.

Email content is untrusted evidence. It cannot select a spreadsheet, recipient, URL, command, scope, class identity or payroll rule. The queue exposes the exact source ID, event and related later replies. A repeated Gmail ID is replayed once; a separate reply repeating a business fact remains separate evidence, not another authorized attendance write. An “actually” reply preserves the earlier message and review. Before any eventual write, the reviewer must compare related replies for superseding or repeated facts.

Immutable message bytes and subsequently observed parent-thread proof are stored separately. A parent appearing on an overlapping scan can advance that same source to review without duplicating it or losing an earlier held decision. Each evidence version has its own immutable review slot. Changed message bytes or conflicting verified parents produce a visible quarantine and do not block later valid messages or checkpointing. Sender-unverified and missing-event records likewise leave metadata-only operator exceptions; their absence from the correction list is never a healthy all-clear. Class identity uses the same Unicode/apostrophe normalization as the actual digest generator.

State boundaries are `received`, `hold`/`dismiss`, and `proposed`. `proposed` is an immutable human review decision and is still held for attendance audit and payroll readback. This pilot has no applied/completed mutation route. Multiple questions, new instructor identities, stale threads and ambiguous language require review. “Josiah for both” on a single known occurrence preserves that occurrence's scope plus an unresolved remainder; it cannot create a second class or guess Josiah's canonical identity.

Cause is separate from receipt or attendance status: `unresolved`, `confirmed-human-omission`, `cancelled-class`, `delayed-upload`, `technical-uncertainty`, or `schedule-uncertainty`. The default is unresolved. Only a reviewed decision assigns a confirmed cause. A correction does not automatically imply negligence. No new staff alerts or policy automation is installed.

`tools/reconcile-m1-reply-payroll.mjs review.json evidence.json new-report.json` is an **offline comparison contract**, not a live payroll integration. Supply independently obtained, verified attendance/audit/payroll exports normalized to the tested evidence schema. It compares source/review/audit links, actual resulting row, gym, date, exact class and instructor, credit, payroll period, duplicate permanent IDs, and superseded rows. It fails held on missing/mismatched evidence and never releases payroll or marks the queue complete. Do not fabricate linkage fields missing from a native export. A production adapter for authoritative row-plus-audit readback is a later gate.

`duration` preserves the existing **payroll credit** meaning. It is not inferred elapsed time; Richmond's 7:15–9 PM class can carry 1 credit rather than 1.75. Raw duplicate sign-ins alone do not establish double payment. Current upstream add logic can match an existing event without matching its credit, and the existing verification endpoint is Revolution-only. Neither an “already exists” receipt nor a Richmond add response proves reconciliation. The October 9 Josiah mutation remains canceled/pending outside this task.

## Self-correcting mechanism

| Fault | Detection | Recovery | Independent check and stopping point |
|---|---|---|---|
| Missed hourly run / expired grant | Durable poll coverage and last checked time; overdue after 3 hours; backlog after 24 hours | Operator repairs existing trigger or Andrew renews the exact approved grant; next run resumes retained interval | A successful new poll and authenticated queue read confirm recovery. Unknown coverage never means zero outstanding. |
| Queue unavailable, crash before write or after write before checkpoint | No confirmed queue acknowledgement; cursor remains unchanged | Next hourly invocation repeats that interval; immutable Gmail ID deduplicates stored messages | Strong readback matches exact retained payload; conflicting source bytes are quarantined without overwriting or blocking later messages. |
| More than one Gmail page | `nextPageToken` prevents checkpoint | Up to eight bounded oldest-first interval subdivisions; incomplete slices remain pending | Over-capacity status and stable exception key; no skipped page is called complete. |
| Malformed reply / wrong identity / missing parent | Strict validation; metadata-only quarantine or held queue record | Goati/operator inspects original authorized business evidence; later good replies continue | No attendance action from a malformed or guessed identity; held items stay visible. |
| Failed review-record write | No durable matching review returned | Retry same source and review ID | Exact readback and immutable decision; a different decision conflicts rather than replacing history. |
| Reminder event registration or routing fails | Private immutable route fault, plus Script Properties transport pointer if server storage fails | Repair event registration; verify a retained event and completed scan; authenticated operator records the recovery and accounts for replies to the old address | A healthy mailbox poll alone cannot clear `route-degraded`. Recurrence creates a new fault. The sender keeps the old Reply-To fallback and existing warning/send-claim policy. |
| Attendance row written but audit missing | Later independent row-plus-audit comparison | Reuse the existing receiver's documented exact replay repair only if separately authorized | Never apply an unrelated/canceled operation. A row alone is insufficient. |
| Corrected row differs from payroll input | Offline comparison checks actual credit/person/class/date, audit and result row exactly once | Reviewer resolves the discrepancy through the existing payroll process | Remains held until independent exports agree. Payroll release is always outside this pilot. |

The intended operational owner is **goati for intake/triage and the existing GiB operator for technical repair; Andrew performs private consent and business decisions**. Confirm goati can actually read this queue before assigning it unattended responsibility. The signed own-gym `handoffs` and `ack-handoff` actions implement a private durable outbox. Its notices contain IDs and fixed instructions, not raw email bodies. `deliverReplyHandoffs` requires an authenticated queue reader and a host-provided durable idempotent wake operation. It acknowledges only a confirmed matching wake receipt. Empty healthy polls create no notice; overlap creates one notice per source/evidence version; repeated failures create one health notice per episode. A recovery followed by another access failure creates a new exception.

**No actual goati transport or schedule is installed.** Local tests prove that adapter contract, not delivery to the existing goati task. The parent must bind the existing authorized host, prove goati reads the same private item, and verify both wake and health delivery (including endpoint outage) before activation. A read failure must surface through that host's independent health channel, never become an empty queue. Do not substitute an hourly LLM automation for this deterministic reader. Routine Gmail/queue polling contains no model call. Review usage is separate and not assumed free.

The scanner has a two-minute settling delay and a ten-minute overlap, independent of unread/inbox labels. It includes read and archived replies. A long outage retains its earlier cursor. Unusually delayed Gmail search indexing outside the overlap requires an operator replay of the affected interval; do not infer absence solely from search. Retention is conservative: this pilot performs no deletion. Queue reads stop explicitly above 10,000 records of a kind; plan retention before extending the pilot indefinitely.

Its capability object reports 0 used credits; a detailed current metering ledger was not available, so that is not a measured remaining-balance guarantee. No billing setting was changed. [Published credit pricing](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/) is 2 credits/10,000 requests, 10 credits/GB-hour of compute, 20 credits/GB outbound bandwidth and 15 credits/production deployment. Measure actual pilot durations and confirm detailed current usage before activation. No claim of zero total cost; no billing change, new service or laptop software installation is authorized by this document.
